= Step 5: Secrets Done Right with External Secrets Operator
include::_attributes.adoc[]

12-Factor rule III says config lives in the environment. The trap is treating
*secrets* like ordinary config: baked into the image, committed to Git, pasted
into a ConfigMap. This step shows why that fails and what to do instead:
the secret lives in a vault, the cluster only holds a short-lived copy, and Git
only contains a *reference*.

== Prerequisites

* xref:03-scc-rbac.adoc[Step 3] completed: the `demo` Deployment is running in `$PROJECT`
* The External Secrets Operator is installed on the cluster. That is a one-time
  platform task (`05-secrets/operator-install.yaml`); developers do not do it

[#secrets-in-images]
== 1. Why a secret in the image is a secret everyone has

*What:* Build a throwaway image that sets a password with `ENV`, then look at it
the way anyone with pull access can.

*Why:* A layer is permanent. Deleting the line in the next commit does not
remove the secret from images already pushed, from caches, or from registries.

[.console-input]
[source,bash]
----
printf 'FROM registry.access.redhat.com/ubi9/ubi-micro\nENV DB_PASSWORD=hunter2\n' \
  | podman build -q --platform linux/amd64 -t leaky:latest -f - .
podman history --no-trunc --format '{{.CreatedBy}}' leaky:latest | grep -i password
----

[.console-output]
[source,text]
----
/bin/sh -c #(nop) ENV DB_PASSWORD=hunter2
----

The same applies to `COPY .env`, `ARG PASSWORD` and credentials echoed in a
`RUN`. Scanners find them, but only after they are already in the registry.

.Verify: Clean up the throwaway image
[%collapsible]
====
[.console-input]
[source,bash]
----
podman rmi leaky:latest
----
====

'''

[#secret-vs-configmap]
== 2. Secret, ConfigMap, and what a Kubernetes Secret really is

* A *ConfigMap* is for non-sensitive settings (`APP_ENV`, feature flags).
* A *Secret* is for sensitive values. It is only *base64-encoded*, not
  encrypted by itself. Anyone allowed to `get secrets` in the project can read
  it, which is exactly why Step 3 withheld that verb from the limited identity.
* ROSA encrypts etcd at rest, which protects the disk, not a user with API access.

So a Secret in Git is still a secret in Git. The rest of this step avoids ever
writing the value anywhere a developer or a pipeline can leak it.

'''

[#eso]
== 3. Reference the secret, never store it

*What:* Declare *which* secret the app needs. The External Secrets Operator
fetches the value from the external store and keeps a native Secret in sync.

*Why:* Git and code review see only a pointer. The value lives in the vault,
where rotation, access policy and audit are already solved. This also gives you
a clean exit from any one provider (DORA Art. 28 asks you to be able to
replace third-party services).

Two objects are involved:

[cols="2,4",options="header"]
|===
| Object | Role

| `SecretStore`
| *How to reach* the vault: provider, region or URL, how to authenticate. Owned by the platform team.

| `ExternalSecret`
| *What to fetch*: which remote key, into which Kubernetes Secret, how often to refresh. Owned by the application team. Contains no secret value.
|===

The workshop uses ESO's built-in `fake` provider so everything runs without a
cloud account. The ExternalSecret is identical for a real provider; only the
SecretStore changes.

[.console-input]
[source,bash]
----
oc apply -f 05-secrets/secretstore-fake.yaml --context rosa -n $PROJECT
oc apply -f 05-secrets/externalsecret.yaml --context rosa -n $PROJECT
oc get secretstore,externalsecret --context rosa -n $PROJECT
----

[.console-output]
[source,text]
----
NAME                                             AGE   STATUS   CAPABILITIES   READY
secretstore.external-secrets.io/workshop-store   9s    Valid    ReadWrite      True

NAME                                         STORETYPE     STORE            REFRESH INTERVAL   STATUS         READY   LAST SYNC
externalsecret.external-secrets.io/demo-db   SecretStore   workshop-store   15s                SecretSynced   True    9s
----

NOTE: The `fake` provider prints a warning that it "isn't currently maintained".
That is expected: it exists for tests and workshops, never for real secrets.

.Verify: The native Secret was created and is owned by the ExternalSecret
[%collapsible]
====
[.console-input]
[source,bash]
----
oc get secret demo-db --context rosa -n $PROJECT -o jsonpath='{.data.DB_PASSWORD}' | base64 -d; echo
oc get secret demo-db --context rosa -n $PROJECT -o jsonpath='{.metadata.ownerReferences[0].kind}{"\n"}'
----

[.console-output]
[source,text]
----
initial-password-v1
ExternalSecret
----
====

[#mount-secret]
== 4. Mount it as files, not environment variables

icon:clock[] ~20 seconds

*What:* Patch the Deployment to mount the Secret read-only.

*Why:* Files are updated by the platform when the Secret changes, so you can
rotate without redeploying. Environment variables are fixed at start, and are
easy to leak through crash dumps, debug endpoints and `docker inspect`-style tools.

[.console-input]
[source,bash]
----
oc patch deployment demo --patch-file 05-secrets/deployment-secret-patch.yaml \
  --context rosa -n $PROJECT
oc rollout status deployment/demo --context rosa -n $PROJECT
POD=$(oc get pod -l app=demo --context rosa -n $PROJECT -o name | head -1)
oc exec $POD --context rosa -n $PROJECT -- cat /etc/demo-secrets/DB_PASSWORD
----

[.console-output]
[source,text]
----
deployment "demo" successfully rolled out
initial-password-v1
----

NOTE: As in Step 3, `oc exec` is used here only to *show* the file. The app
would read it itself.

'''

[#rotation]
== 5. Rotate the secret without touching the app

icon:clock[] ~1-2 minutes (the kubelet refreshes mounted Secrets periodically)

*What:* Change the value in the store, the way a vault rotation would.

*Why:* This is the payoff. Rotation becomes a vault operation, not a
redeploy. Short-lived, regularly rotated credentials limit the damage of any
leak (DORA Art. 9, protection and prevention).

[.console-input]
[source,bash]
----
oc patch secretstore workshop-store --type merge --context rosa -n $PROJECT \
  -p '{"spec":{"provider":{"fake":{"data":[{"key":"/demo/db-password","value":"rotated-password-v2"}]}}}}'
sleep 25
oc get secret demo-db --context rosa -n $PROJECT -o jsonpath='{.data.DB_PASSWORD}' | base64 -d; echo
----

[.console-output]
[source,text]
----
rotated-password-v2
----

The Secret updated within the 15 second refresh interval. The *file in the
running pod* follows shortly after, with no restart:

[.console-input]
[source,bash]
----
until [ "$(oc exec $POD --context rosa -n $PROJECT -- cat /etc/demo-secrets/DB_PASSWORD)" = rotated-password-v2 ]; do sleep 10; done
oc exec $POD --context rosa -n $PROJECT -- cat /etc/demo-secrets/DB_PASSWORD
----

[.console-output]
[source,text]
----
rotated-password-v2
----

In our run the file changed about 70 seconds after the store did.

.Verify: The pod was never restarted
[%collapsible]
====
[.console-input]
[source,bash]
----
oc get pods -l app=demo --context rosa -n $PROJECT
----

The `RESTARTS` column is still `0`: the new value reached the running container
through the volume.
====

'''

[#real-providers]
== 6. Real providers: AWS Secrets Manager and Azure Key Vault

The only file that changes is the `SecretStore`. The repository contains both,
*not exercised in this workshop cluster* (they need real cloud accounts):

[cols="2,3,3",options="header"]
|===
| | AWS Secrets Manager | Azure Key Vault

| Manifest
| `05-secrets/secretstore-aws.yaml`
| `05-secrets/secretstore-azurekv.yaml`

| Authentication
| The ServiceAccount is exchanged for an IAM role (IRSA/STS). No long-lived keys in the cluster.
| Service principal client id and secret stored in a Secret, or workload identity federation if your tenant allows it.

| Fit on ROSA
| Native: same cloud as the cluster, IAM roles scoped per secret.
| Works, but crosses clouds. The Azure credential is itself a secret to protect and rotate.

| Remote key
| Secrets Manager secret name
| Key Vault secret name
|===

TIP: Whichever backend you choose, scope its policy per application to the
specific secrets it needs. A SecretStore with read access to the whole vault
repeats the "wildcard RBAC" mistake from Step 3.

IMPORTANT: DORA angle. The vault and the operator are ICT third-party services
and components. Art. 28 asks you to know, assess and be able to exit them; this
design keeps the exit cheap, because the application only knows a Kubernetes
Secret. Contractual terms with the cloud provider (Art. 30) belong to your
compliance and procurement teams.

== What This Solves

[cols="2,3",options="header"]
|===
| Problem | How this step solves it

| Secrets baked into images or committed to Git
| Only a reference is in Git; the value lives in the vault

| Rotating a credential means a redeploy
| Rotation reached the running pod in about a minute, with no restart

| Developers can read production secrets
| Developers own the `ExternalSecret`; access to the vault stays with the platform team
|===

== What This Does NOT Solve (Yet)

[cols="2,3",options="header"]
|===
| Remaining problem | Addressed in

| Any pod in the cluster can still call any other pod's network port
| xref:06-network.adoc[Step 6]: NetworkPolicy and internal versus external applications

| Anyone with `get secrets` can still read the synced Secret
| Step 3 RBAC: do not grant it; audit who has it
|===

== Alternatives Considered

[cols="2,4",options="header"]
|===
| Approach | Notes

| This: External Secrets Operator syncing into native Secrets
| Provider-neutral, app unchanged, rotation without redeploy. Secret exists in etcd (encrypted at rest).

| Secrets Store CSI Driver
| Mounts secrets straight from the vault into the pod, optionally without ever creating a Kubernetes Secret. Stronger isolation, but the app must use the mounted files and not every provider feature is available.

| Sealed/encrypted secrets in Git (GitOps)
| Fine for GitOps teams; rotation and central audit are weaker than a vault.

| Plain Secrets in Git or in the image
| Never.
|===

== Reset

[.console-input]
[source,bash]
----
oc patch deployment demo --type json --context rosa -n $PROJECT \
  -p '[{"op":"remove","path":"/spec/template/spec/volumes"},{"op":"remove","path":"/spec/template/spec/containers/0/volumeMounts"}]'
oc delete externalsecret demo-db --ignore-not-found --context rosa -n $PROJECT
oc delete secretstore workshop-store --ignore-not-found --context rosa -n $PROJECT
----

The operator itself stays installed: it is a cluster-level platform component.
