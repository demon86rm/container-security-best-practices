= Step 4: Shift-Left Scanning and Policy Gates
include::_attributes.adoc[]

Steps 2 and 3 made security a human decision: you chose a good Containerfile,
you chose a non-root user, you read the SCC error. This step makes it a *machine* decision. The idea
is one sentence: find out whether an image or manifest is acceptable at build
time, in the pipeline, before it can ever reach a cluster.

== Prerequisites

* xref:03-scc-rbac.adoc[Step 3] completed (the concepts build on it; the commands below do not need the cluster)
* A RHACS Central you can reach and an API token with the *Continuous Integration* role (see the token note below). Steps 5 and 6 do not depend on this step

[#policy-lifecycle]
== 1. The policy lifecycle: build, deploy, runtime

*What:* Learn the three moments at which a security policy can act.

*Why:* Knowing where a control sits tells you who owns it and how early a
problem can be caught.

Modern cluster security tooling enforces the *same* policy at three moments.
Knowing the three moments is most of the conceptual content of this step.

[cols="2,3,2,2",options="header"]
|===
| Stage | When it fires | What can happen | Developer-relevant tool

| Build
| A pipeline scans the image before it is pushed/promoted
| The CI job fails; the image never ships
| `roxctl image check`, scanner plugins in any CI

| Deploy
| The cluster API receives a manifest
| The admission webhook rejects it (hard) or scales it to zero (soft)
| Admission controller in RHACS; SCCs in OpenShift (Step 3)

| Runtime
| A live process or connection does something the policy forbids
| The pod is terminated, the violation is recorded
| eBPF-based collectors (e.g. RHACS Collector)
|===

Two terms to keep straight: *hard* enforcement blocks the action outright;
*soft* enforcement lets the object in but neutralizes it (replicas scaled to
zero), which is how teams roll out a new policy without breaking the pipeline
on day one. Both are better than discovering the problem in an incident
review.

The developer takeaway: the build stage is yours. The deploy and runtime
stages are the platform team's. Shift-left means you do not have to wait for
either of them to tell you that the build was bad.

TIP: DORA angle. A pipeline that emits a CVE report and an SBOM for every image
is evidence that exists *before* the image is deployed: the SBOM supports your
ICT asset inventory (Art. 8), the scan supports patching (Art. 9) and
vulnerability scanning (Art. 25), and the pipeline gate is how you make
those checks repeatable instead of occasional.

[#roxctl-gate]
== 2. The roxctl CI gate

*What:* Wire a scan, an SBOM and two policy checks into any CI job.

*Why:* The exit code is the gate: a violated policy stops the pipeline before
the image is pushed.

Red Hat Advanced Cluster Security for Kubernetes (RHACS, built on the upstream
StackRox project) exposes the
build- and deploy-stage evaluation as a CLI, `roxctl`. Its exit code makes it a
drop-in gate for *any* CI system: Jenkins, GitLab CI, Azure DevOps, GitHub
Actions, or a developer laptop. That portability is the point of the
workshop's chosen example.

The gate, as plain commands (this is the whole integration):

[.console-input]
[source,bash]
----
# 1. Reports, never fail the job, kept as CI artifacts
./roxctl image scan  --image "$IMAGE" --output csv > image-scan.csv
./roxctl image sbom  --image "$IMAGE"             > sbom.spdx.json

# 2. Gate 1: build-time policies. Non-zero exit = job fails
./roxctl image check --image "$IMAGE" --output junit > image-check.junit.xml

# 3. Gate 2: deploy-time policies, against the manifests you are about to ship
./roxctl deployment check -f 03-scc-rbac/deployment.yaml \
  --output junit > deployment-check.junit.xml
----

Report formats worth knowing: `junit` for CI test-report views, `sarif` for
code-scanning dashboards, `csv`/`json` for custom processing, `table` for
humans in the log.

The repository ships the whole thing as one script:

[.console-input]
[source,bash]
----
less 04-shift-left/rox-ci-gate.sh
----

It needs only `bash` and `curl` (it downloads a `roxctl` matching the Central
version), reads three environment variables - `ROX_ENDPOINT`, `ROX_API_TOKEN`,
`IMAGE` - writes reports to `rhacs-reports/`, and exits non-zero when an
enforced build- or deploy-time policy is violated. The CI wiring for
GitHub Actions, for reference:

[.console-input]
[source,bash]
----
less 04-shift-left/github-actions-example.yaml
----

Two operational details that matter in practice:

* *Token hygiene.* The gate uses an API token with the read-only
  **Continuous Integration** role, stored as a masked CI secret. Never an
  admin token in a pipeline.
* *One rule set.* Because the build gate and the cluster admission controller
  evaluate the *same* policy definitions, an image the cluster would reject
  never gets built and pushed. No drift between "CI says yes" and "the cluster
  says no".

NOTE: The workshop does not install RHACS: the platform team owns Central. The
`rhacs-reports/` artifacts - CVE CSV, SPDX SBOM, JUnit policy results - are the
DORA-facing evidence.

[#run-gate]
=== Run it against your Central

Export the three required variables, plus the two optional ones that tell
`roxctl deployment check` which cluster and namespace the manifest is for
(namespace-scoped policies only match when it is set). Keep the token out of
Git and out of your shell history, for example by exporting it from a secret
store:

[.console-input]
[source,bash]
----
export ROX_ENDPOINT=<central-host>:443
export ROX_API_TOKEN=<token with the Continuous Integration role>
export ROX_CLUSTER=<cluster name in Central>
export ROX_NAMESPACE=$PROJECT
export IMAGE=registry.access.redhat.com/ubi9/ubi-micro:latest
export MANIFESTS=03-scc-rbac/deployment.yaml
./04-shift-left/rox-ci-gate.sh; echo "exit: $?"
----

Console output captured on OpenShift 5.0 with RHACS 5.0 (long tables trimmed to
the summary lines; a `roxctl` 4.11 client was used):

[.console-output]
[source,text]
----
Scan results for image: registry.access.redhat.com/ubi9/ubi-micro:latest
(TOTAL-COMPONENTS: 4, TOTAL-VULNERABILITIES: 3, LOW: 0, MODERATE: 0, IMPORTANT: 3, CRITICAL: 0)
WARN:	A total of 3 unique vulnerabilities were found in 4 components
ERROR:	checking image failed: failed policies found: 1 policies violated that are failing the check
Policy check results for image: registry.access.redhat.com/ubi9/ubi-micro:latest
(TOTAL: 3, LOW: 2, MEDIUM: 0, HIGH: 1, CRITICAL: 0)
...
ERROR:	Policy "Fixable Severity at least Important" - Possible remediation: "Use your package manager to update to a fixed version in future builds or speak with your security team to mitigate the vulnerabilities."
Policy check results for deployments: [demo]
(TOTAL: 1, LOW: 1, MEDIUM: 0, HIGH: 0, CRITICAL: 0)
RHACS gate: FAILED. Enforced policy violations found (see reports in rhacs-reports/).
exit: 1
----

The row that broke the build is "Fixable Severity at least Important", marked
`X` in the *BREAKS BUILD* column: the base image carried an Important
vulnerability with a fix available (`libacl`), so the job fails and the image
never ships. The two LOW findings (a root user in the image metadata and the
`latest` tag) are reported but do not break the build. A base image without a
fixable Important finding passes: with
`IMAGE=registry.access.redhat.com/ubi10/ubi-micro:latest` the run ends with

[.console-output]
[source,text]
----
Policy check results for image: registry.access.redhat.com/ubi10/ubi-micro:latest
(TOTAL: 2, LOW: 2, MEDIUM: 0, HIGH: 0, CRITICAL: 0)
...
RHACS gate: PASSED
exit: 0
----

and `rhacs-reports/` holds `image-scan.csv`, `sbom.spdx.json` (SPDX 2.3),
`image-check.junit.xml` and `deployment-check.junit.xml`.

IMPORTANT: The result depends on the vulnerability data of the day. New
advisories and rebuilt base images change the answer without any change in your
code (right after a Central upgrade, scans of the same images even came back
with no components until the scanner finished loading its data). That is the
point of the gate: rebuild on a schedule, not only on commit.
Which policies actually break the build is a Central setting owned by the
platform team: a gate with no enforced policy exits `0` whatever it finds.

.Verify: The gate script is sound
[%collapsible]
====
*What:* Confirm the script fails fast when it is misconfigured.

*Why:* A gate that silently passes when it cannot reach its policy source is
worse than no gate.

[.console-input]
[source,bash]
----
bash -n 04-shift-left/rox-ci-gate.sh && echo "syntax OK"
ROX_ENDPOINT= IMAGE= ./04-shift-left/rox-ci-gate.sh; echo "exit: $?"
----

[.console-output]
[source,bash]
----
syntax OK
./04-shift-left/rox-ci-gate.sh: line 21: ROX_ENDPOINT: ROX_ENDPOINT is required
exit: 1
----

The script fails fast on missing configuration - exactly the behavior you
want from a gate.

[#tool-comparison]
== 3. Tooling comparison: RHACS, XRay, AWS Inspector

*What:* Place three common tools on the map.

*Why:* You will be asked how this compares to what your organization already
owns.

You will be asked how this compares to other scanners. The honest answer is
that they sit at different layers, and a DORA-grade setup often uses more than
one.

[cols="2,2,2,2",options="header"]
|===
| | Red Hat RHACS (`roxctl`) | JFrog XRay | AWS Inspector

| What it is
| Kubernetes-native security platform: CVE scanning plus *policy* at build, deploy, and runtime
| Repository and artifact-level intelligence for software supply chains (containers, languages, SCA)
| Vulnerability and configuration assessment for AWS workloads and ECR images

| Where it sits
| Pipeline (CLI), cluster admission (webhook), node (runtime collectors)
| Your artifact repository (JFrog Artifactory), plus CI plugins
| AWS account; ECR image scanning, plus agent-based EC2/Container insights

| Policy enforcement
| Yes: named policies with lifecycle stages, hard or soft enforcement, exceptions workflow
| Yes, at the repository/CI level: quality and security checks gate builds
| Findings and findings-based recommendations; enforcement via AWS-native controls (e.g. ECR image scan on push)

| K8s runtime visibility
| Yes: process and network monitoring, network graph
| No
| Limited (via integrations)

| Natural fit
| OpenShift estates; cluster-level rule sets
| Organizations already running an Artifactory-centric pipeline
| AWS-heavy estates scanning ECR images and EC2
|===

Reading the table in one sentence: they are complementary, not rivals - XRay
can police the repository, ACS can police the cluster (and its pipeline), and
AWS Inspector covers the AWS substrate - and DORA does not care which brand
produces the evidence, only that you have it.

NOTE: On OpenShift, the lowest-friction first step is usually image
scanning with a tool you already have (the RHACS gate above if you have a
Central; XRay if you run Artifactory), plus the SBOM as a standing CI
artifact. Adding a second tool later is a policy-migration conversation, not
a re-architecture.

== Alternatives Considered

[cols="2,4",options="header"]
|===
| Approach | Notes

| This: roxctl build + deploy gate, CI-agnostic
| One CLI, same policies as the cluster admission, portable across CI tools. Chosen for the workshop because it demonstrates the full build/deploy lifecycle.
| `osv-scanner`/`grype`/`trivy`-style standalone scanners in CI
| Fine for CVE detection alone; no deploy-stage policy evaluation and no runtime layer. Good as a first step before adopting a platform.
| Relying only on cluster-side admission (Step 3 controls)
| Catches violations at deploy time, but after the image has been built, pushed, and stored. Later in the lifecycle than necessary.
